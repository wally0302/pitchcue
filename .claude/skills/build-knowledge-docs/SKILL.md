把專案原始資料寫成 `data/` 知識文件，讓 `/api/answer` 在評審提問時能用團隊自己的說法、正確的數字、誠實的限制回答。

**輸入**：一個或多個來源（資料夾、簡報 PDF、文件、repo）。可帶專案名稱與活動名稱。

## 這個系統怎麼吃文件（寫之前一定要知道）

- `scripts/build-knowledge.mjs` 讀 `data/` **根目錄**的 `*.md|*.txt`，依檔名數字排序、全文合併，每份包成 `<document name="檔名">`，放在 system prompt 最末。子資料夾不讀；`README.md`、`glossary.txt` 排除。
- 沒有檢索、沒有截斷、沒有大小上限。整份語料每次都送，靠 prompt cache。目標總量 25k 到 40k 字元。
- 檔名對模型可見，檔名就是索引，用評審會問的主題命名。
- `glossary.txt` 一行一詞，前 50 個進語音辨識 keywords，全部進問題整理的詞彙表。同音易錯的專有名詞放最前面。
- `lib/prompts.ts` 的 ANSWER_SYSTEM 已規定輸出「## 重點」「## 口語稿」、只依文件回答、不捏造、結構為「直接回答 → 證據 → 承認限制 → 下一步」。文件不用重複這些，要做的是把事實與說法餵進去。
- 改完 `data/` 要跑 `npm run knowledge`，部署前要換 `PROMPT_CACHE_KEY`（`.env.local` 與 Vercel）。

## 步驟

1. **盤點來源**。用 Explore agent 把來源全部讀過，產出：專案一句話、痛點與數字、架構與服務、資料流、已做／未做、demo 素材、已知限制、團隊。每個數字記下出處與日期。**特別列出來源之間互相矛盾的地方**（模型、筆數、功能有無、舊簡報與新程式碼）。

2. **裁決衝突，問使用者只有他能答的事**。原則：程式碼與日期最新的文件優先；簡報與早期會議紀錄是「構想」。用 AskUserQuestion 一次問完：團隊要不要寫姓名、商業或落地定位、數字有衝突時以哪個為準、還有沒有來源裡沒有的事實（試用回饋、成本）。不要猜。

3. **寫八份文件**（結構見 `references/file-structure.md`）：
   - `00-回答規則與數字速查.md`：回答原則、禁句對照表、數字速查表（每個數字帶標籤：★實測／估算＋假設／命題／目標／設定）、已解決的版本衝突、「文件裡沒有的東西」。這份是單一真相，其他檔案的數字必須與它一致。
   - `01` 專案簡介與定位、`02` 核心流程與人機分工、`03` 架構與技術決策、`04` 資料處理與檢索（依專案調整主題）、`05` Demo 案例與現場測試（含簡報逐頁可能被追問的點）、`06` 已知限制與後續規劃、`07` 常見問題（約 50 題，依評分面向分組，結尾「希望評審記住的三件事」）。
   - 每個 `##` 第一段是 60 到 120 字可直接唸的證據句。每份技術文件結尾有「這份文件範圍外，不要延伸」。
   - 全文台灣繁體中文、第一人稱「我們」、人物只用角色（除非使用者要求寫姓名）。
   - 沒有數據的題寫「目前沒有數據。現況是……。計畫是……」，不要留白，也不要把目標值寫成成果。

4. **寫 glossary.txt**：先同音易錯的領域名詞，再產品／隊名，再雲端服務名，最後縮寫。目標 50 到 100 個。

5. **簡報進來時**：逐頁讀（PDF 用 `references/render-pdf.md` 的方法），在 `05` 加「簡報逐頁可能被追問的點」，在 `07` 加「針對簡報畫面的追問」，把簡報與程式碼的出入寫進 `00` 禁句表。簡報上寫了但沒實作的東西，答法固定是「那頁是規劃／設計流程，實際現況是……」。

6. **驗證**（每次改完都做）：
   - `npm run knowledge`，看檔案數與字元數。
   - `bash .claude/skills/build-knowledge-docs/scripts/scan.sh`：禁句掃描，命中只能在 `00` 的「不要說」欄、問題句、或「不要說」段落。
   - `python3 .claude/skills/build-knowledge-docs/scripts/battery.py`：起一個臨時 dev server 跑題庫（含陷阱題、追問題、範圍外題），逐題對照 `00` 人工評分。跑完一定關掉 server，不留閒置流程。
   - 修正後再跑一次受影響的題。

7. **交付**：列出寫了哪些檔案、裁決了哪些衝突、哪些題是「目前沒有數據」需要使用者補、簡報上哪些地方跟現況不符要上台前決定。不主動 commit，除非使用者要求。

## 寫作規則（違反任何一條就是錯）

- 每個數字都要能在 `00` 找到同值與標籤。
- 不寫任何未實測的準確率、召回率百分比。
- 不把舊簡報或會議紀錄裡的構想寫成已做。
- 被質疑型問題先承認，說明型問題直接答，不要每題都用「評審點到的風險是真的」開頭。
- 禁句表要給「改說」版本，不能只寫「不要說」。
- 檔名前綴兩位數字，`00` 是規則、最後一份是 FAQ。
